## 1. Three ceilings you will hit without warning

These are the ones that stop the tool dead rather than degrade it. All three are cheap to fix now
and expensive to fix under pressure.

### 1.1 You are at 12/12 Vercel serverless functions — the next endpoint breaks the deploy

`api/` contains exactly twelve routed functions (`assets, billing, brain, generate, image, kit,
paystack, postiz, projects, scrape, transcribe, upload`; `_ai.js` and `_guard.js` are excluded by
the underscore). Vercel's Hobby tier caps at 12. **Verified by count.**

The failure mode is nasty: you add one feature, the deploy fails, and the cause looks nothing like
the change you made. It also means every future capability — publish-to-Postiz, webhooks, a
public share link, per-user auth — is blocked on a refactor you'll be doing in a hurry.

**Fix:** collapse the small, related endpoints behind one catch-all router
(`api/v1/[...path].js`) that dispatches to plain modules under `api/lib/`. Start with the four
that are barely more than a fetch proxy (`kit`, `image`, `upload`, `scrape`). That buys headroom
back to ~8/12 and costs no behaviour change, because `_guard.blocked()` already sits at the top of
each handler and can move to the router. Do this **before** the next feature, not after.

### 1.2 Spend has no hard ceiling in the app any more

`_guard.js` rate limiting falls back to a per-instance in-memory `Map` when Upstash isn't
configured, and it **fails open** on error — by design, so a Redis blip never blocks you. Upstash
is still not configured (memory note + no env reference in the repo). As of this session the free
plan is also uncapped (`PLANS.free.aiLimit = -1`), which you asked for and which is correct while
there's no billing — but it means the *only* thing standing between a runaway loop, a leaked
session token, or an over-enthusiastic colleague and a five-figure bill is the provider dashboards.

**Fix, in order:**
1. **Hard spend caps + budget alerts on Gemini, Groq and Vercel today.** This is the real backstop
   and it's a 15-minute job. Not a recommendation — a prerequisite for leaving the app running.
2. Add the two free Upstash env vars (`UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`) so
   rate limiting is global and durable instead of per-warm-lambda.
3. Keep usage metered (it is) and put the monthly number somewhere you'll actually see it — the
   Settings panel is behind three clicks. A line on the Create home screen would do it.

### 1.3 Model names are hardcoded defaults with no health check

`api/_ai.js` defaults to `gemini-2.5-flash`, `llama-3.3-70b-versatile`, `llama-3.3-70b`,
`meta-llama/llama-3.3-70b-instruct:free`. **Verified.** When a provider retires a model — and they
retire them on roughly 12-month cycles — Volt starts returning provider errors and the only signal
is a user complaint.

The mitigation that already exists is genuinely good: `_ai.js` implements a **multi-provider
fallback chain** (Gemini → Groq → Cerebras → OpenRouter). That's better resilience than most
solo-built tools have, and it means a single provider outage degrades rather than breaks.

**Fix:** a `/api/health` style check already exists (`health.html`) — extend it to make one cheap
real call per configured provider and report which models actually answer. Then you find out on a
Tuesday morning instead of mid-send.

## 2. The verification gap — this is the one that's already costing you

This is my main technical criticism, and it's the honest read on why the bugs you flagged this week
reached your list.

**What happened, factually:** `smoke.html` renders all 107 designs and asserts "didn't crash,
non-blank, correct dimensions". It reported **107/107 PASS** while simultaneously shipping:

- a white CTA button with a white label (invisible) on the Serv brand
- an invisible verification badge on the same brand
- `serv.co.za` printed across the "Compare Quotes" button
- a landscape banner with no headline at all (`findpros.c` stores its headline under `category`,
  which the wide layout never read)
- portrait designs rendered as a floating card inside flat dead bands
- email sections inheriting the client's default font because they set a size but no face

Every one of those is *visually obvious* and *invisible to the current checks*. The tests aren't
wrong, they're measuring the wrong thing: "the canvas has ink on it" is not "the design is
correct."

**Second finding:** the smoke matrix was also testing `providers`/`findpros` directions **D and E**,
which have never existed in the registry — they silently fell through to the A branch. So it was
reporting 30 renders of coverage it didn't have. Fixed this session, but it's a good illustration:
a test that can't fail isn't a test.

**Fix (ranked by value per hour):**

1. **A second brand in every render test.** Volt's colours come from the active Brand Kit, so
   "dark navy on white paper" is an assumption, not a fact. Every contrast bug above was a
   light-secondary brand (Serv). One extra loop over a `{primary:#3d1152, secondary:#e9e9ec}`
   brand would have caught all four. **Cheapest, highest-value change on this list.**
2. **Assert on geometry, not just ink.** You already have the fits and wraps in code; have the
   worker also emit the bounding boxes it drew and assert (a) nothing overlaps the CTA band,
   (b) no text-vs-background pair is under 3.0 contrast, (c) no more than N% of the canvas below
   the last content line is empty. That is ~80 lines and it turns three of this week's bugs into
   red builds.
3. **Put it in CI.** `smoke.cjs` (syntax + tag balance) and `smoke.html` (renders) both exist and
   both pass locally. Neither runs on push. A GitHub Action on `main` that runs `smoke.cjs` and a
   headless `smoke.html` costs nothing and means a broken deploy can't reach the desktop app —
   which, remember, auto-updates from Vercel on next open.
4. **A golden-image diff.** Once (1)–(3) are in, store the 107 PNG hashes. Then any *unintended*
   visual change to any design shows up as a diff, and intended ones are a one-line hash update.

There is also a hard constraint worth writing down: **screenshots time out in this environment**, so
"looks fine" cannot be automated the easy way. The workaround that does work is rendering to blobs
and inspecting them out-of-band. Whatever you build, build it so the output can be *looked at*, not
just asserted on.

## 3. The moat may not be filling up — verify this first

Your own strategy note says it plainly: the defensible asset is not features, it's **per-org
performance-labelled content history** plus the 60k-person distribution list. The code to capture

But `logContent()` ends in `catch (e) { return null; }` — **verified**, `api/_guard.js`. Every

I cannot check this from here. **Please verify today:**

```sql

```

If those are zero or empty, the last few months of "building the moat" produced nothing, and the

counter surfaced on `health.html` ("content_item writes: 412 ok / 0 failed this instance") converts

## 4. Security — what's genuinely good, and the one hole left

**Good, and better than I expected:**
- Real session auth (`requireSession`: Supabase bearer token verified against `/auth/v1/user`),
  not a shared client secret. Domain allowlist via `ALLOWED_EMAIL_DOMAIN`.
- `blocked()` **fails closed** (503 if Supabase env is missing) — the legacy app-key branch was
  retired.
- `scrape.js` has an actual SSRF guard (protocol allowlist + private-host rejection). Most
  hand-rolled scrapers don't.
- Provider keys are per-org and encrypted (AES-256-GCM) rather than shared in the clear.
- `upload.js` enforces `image/*` + 5MB; `transcribe.js` caps at 26MB.
- Electron: `contextIsolation: true`, `nodeIntegration: false`. Correct.

**The hole:** `main.js:199` sets `webSecurity: false`, and `main.js:210` loads the app from
`https://tshephos-lab.vercel.app/desktop/home.html`. So the desktop app runs **remote code with
same-origin enforcement disabled**. The reason is documented and legitimate (cross-origin template
images taint the export canvas), but the consequence is that a compromise of that Vercel
deployment — or DNS, or a dependency that injects a script — executes in a Chromium that won't
stop it, on a machine that has the user's API keys in localStorage.

**Fix:** the canvas-taint problem has a clean solution that doesn't require disabling web security —
proxy external images through your own origin. You already have `api/scrape.js` and `api/assets.js`;
route template/brand images through one of them, serve them same-origin, then flip
`webSecurity: true`. It's a contained change and it closes the only structural security issue I
found.

**Minor:** the retired `APP_KEY` (`volt_8cdecf…`) is still embedded in six client HTML files
(`analytics, campaign, email, health, index, video`) — **verified**. It's no longer enforced, so
it's not exploitable, but a dead credential in source invites someone to "reuse the existing key"
later. Delete it.

## 5. Maintainability — the slow threat, and the real answer to "next 5-10 years"

The numbers: **16,041 lines** across the web app. `studio.html` alone is **4,282 lines**,
`email.html` 2,561, `video.html` 2,369. No build step, no modules, no dependency management on the
front end, one smoke page for tests. 205 commits, **121 of them in the last 30 days.**

That velocity is the point — the no-framework, single-file, zero-build choice is *why* a two-person
operation ships this fast, and I want to be clear that I'd make the same call again for the first
year. It is genuinely the right architecture for finding out what the product is.

It is not the right architecture for year three. The failure mode isn't a crash, it's arithmetic:
every change to `studio.html` requires holding 4,000 lines in your head, so the cost of each
improvement rises until improvement stops. You can already see it in this session — the premium
design system needed a shared geometry layer (`pGeom`/`pSolid`) precisely because 24 designs had
independently hardcoded the same constants. That refactor was overdue, and there are two more like
it waiting (the email block builders, the video draw loop).

**This — not any competitor — is the main threat to Volt being relevant in 5-10 years.** A solo-
maintained 16k-line codebase with a bus factor of one and no test net either gets restructured or
gets abandoned and rewritten. Rewrites are where products die.

**Fix — and deliberately not "rewrite it in React":**
1. **Extract, don't rewrite.** Pull the worker canvas engine out of `studio.html` into
   `studio-engine.js` (it's already cleanly separated by the `<script id="worker-src">` boundary,
   so this is a cut-and-paste plus a fetch). Same for the email block builders → `email-blocks.js`.
   Two files, two afternoons, and `studio.html` drops by ~2,000 lines. No framework, no build step,
   no behaviour change.
2. **Then the tests from §2 can target those modules directly** instead of scraping them out of an
   HTML file with a regex — which is what both `smoke.html` and my review harness have to do today.
3. **Write down the invariants.** The premium geometry rules, the "never assume brand colours are
   dark-on-light" rule, the `_voltHandoff` precedence rule, the email typography rule. Some of
   these now live in code comments, which is the right place — keep doing that, because it's what
   lets a future maintainer (or a future AI session) not re-break them.

## 6. Product & competitive position

### What's actually defensible

Not the features. A copy generator, a canvas engine and a caption tool are all commodity in 2026,
and will be more so. What's defensible:

1. **Distribution.** A 60,000-person SA SME list is the asset. It cannot be bought quickly and it
   cannot be copied.
2. **South African specificity.** CIPC, B-BBEE, PayFast/Yoco/iKhokha, SARS, township-market
   context, R-denominated funding. Canva will never localise this deeply for a market this size.
   Every design family you've built (funding, providers, findpros, merch, podcast) encodes SA
   context that a global tool won't.
3. **Owned performance data.** Which hook worked, for which SA audience, at what time. See §3 —
   this only counts if it's actually recording.
4. **Workflow lock-in.** Saved brands, drafts, looks, hand-offs between tools. The autosave work
   this session materially increases this: a tool that never loses your work is one you keep using.

### Threats, ranked by likelihood × damage

| Threat | Read |
|---|---|
| **Canva/Adobe/Meta bundle this for free** | Near-certain, already happening. Feature parity is a losing race — do not run it. Your answer is §6.1–6.3, not more tools. |
| **The moat isn't recording** (§3) | Unknown until you run that query. If true it's the biggest single problem in this document. |

**Build:**

  MediaRecorder, so a 60-second short takes 60 seconds to export. It's the most-felt quality gap

**Don't build:**

### The commercialisation blocker nobody's mentioned

`resolveOrg()` keys an organisation to the **email domain**. That's exactly right for one team on

This isn't urgent (you're internal-only), but it *is* a hard blocker on ever charging for this, and
it's much cheaper to fix before there's data to migrate: treat free-mail domains as per-user orgs,
and make org membership explicit (invite-based) rather than inferred.

## 8. Faster-than-real-time video export — spec, not shipped

This is the one §7 item I did not implement, and I want to be explicit that it was a decision rather
than an oversight.

**Why not:** it is a rewrite of the export path in the module you use most, and I cannot test any of
it from here — no clip to export, no way to run Electron, no way to run ffmpeg, and screenshots time
out so I can't even look at the output. Shipping ~400 lines of untested code through the critical
path and calling it done would be worse than leaving it. It needs a session where you can export a
real clip and watch it.

**Why it's slow today:** `video.html` builds a `MediaRecorder` over `cv.captureStream(30)` plus a
Web Audio destination. Both video frames and audio are captured in wall-clock time, so a 60-second
short takes 60+ seconds and the tab has to stay focused. There is no flag to make that faster —
MediaRecorder assigns timestamps from the clock, so pushing frames faster just produces a shorter
video.

**The design that works, and why each piece is chosen:**

1. **Extract source frames with ffmpeg, don't seek the video element.**
   `ffmpeg -ss <trimStart> -t <dur> -i clip.mp4 -vf fps=30 frames/%05d.png`
   The obvious approach — stepping `videoEl.currentTime` frame by frame — is a trap: each seek costs
   10–50 ms and is not frame-accurate, so 1,800 frames is both slow and subtly wrong. ffmpeg decodes
   sequentially, which is the fast path, and it's already bundled (`ffmpeg-static`, used by
   `volt:to-mp4`).

2. **Composite each frame on the existing canvas engine.** Load frame N as an `ImageBitmap`, run the
   *same* draw code the preview uses (look, captions, hook, name tag, progress, intro/outro), and
   emit a PNG. No playback, so this runs as fast as the CPU draws — and reusing the existing draw
   path is what keeps the export identical to the preview.

3. **Mix audio offline, not in real time.** `OfflineAudioContext` renders the clip audio + music mix
   deterministically and faster than real time; export it as WAV. This also removes the current
   requirement to keep the tab focused, and kills a whole class of "the music was quiet that time"
   bugs, because an offline render is reproducible.

4. **Mux with ffmpeg.**
   `ffmpeg -framerate 30 -i frames/%05d.png -i mix.wav -c:v libx264 -preset veryfast -crf 20 -pix_fmt yuv420p -c:a aac -b:a 192k -movflags +faststart out.mp4`
   No JS muxer needed — writing an MP4 muxer by hand is not a casual undertaking, and ffmpeg is
   already there.

**Expected:** roughly 3–5× faster for a 60 s 1080p short (a few seconds to extract, most of the time
compositing, a few seconds to encode), no focus requirement, and reproducible output.

**Constraints to respect when it's built:**
- **Desktop only.** The web build has no ffmpeg, so `MediaRecorder` must stay as the web path and as
  the desktop fallback. Ship it as an opt-in "Fast export" until it has produced correct files a few
  times, then make it the default.
- **Temp-file hygiene.** 1,800 PNGs is ~1–2 GB; write to `os.tmpdir()`, stream rather than buffer,
  and clean up in a `finally` even on cancel.
- **Two new IPC handlers**, both validating their inputs like `volt:fetch-clip` does:
  `volt:extract-frames` and `volt:encode-frames`.
- **Progress and cancellation** are not optional at this duration — report frames done, and make
  cancel actually kill the child process.
- **Verify frame-count parity** between what the compositor emitted and what ffmpeg consumed. A
  silent off-by-one shows up as audio drift near the end, which is exactly the kind of bug that
  reaches the list.
